# ADR-0001: dsh-compare architecture decisions

## Status

Accepted

## Context

dsh-compare is a local web app that runs one task on two AI models and compares the runs live so a user can see how each model handles the same task. The two runs must proceed concurrently in the browser without conflicting, so the comparison finishes in roughly the slower model's wall-clock time rather than the sum of both.

## Decisions

1. **Transport: WebSocket.** The app is a Node `http` server (bound to 127.0.0.1 on a configurable port defaulting to 4173) that opens a WebSocket connection per browser tab using the `ws` package. WebSocket was chosen over Server-Sent Events or plain HTTP polling because the app needs real-time bidirectional messaging: the browser sends the submitted run and cancel commands, and the server streams live events (text deltas, tool calls, turn ends) back to the owning lane. One connection carries the whole conversation.
   _Rejected: Server-Sent Events_ — one-way delivery, so a separate out-of-band channel would be needed for cancellation and run control.
   _Rejected: HTTP polling_ — adds latency to every live update and complicates per-tab state tracking.

2. **Per-tab run model.** A run is bound to the WebSocket connection that submitted it. There is no server-side run registry; the connection is the run's identity. Each tab runs an independent comparison, and closing or refreshing the tab cancels only that tab's run — on disconnect the server aborts the run bound to that connection.
   - _Rejected: a server-side run registry keyed by run id_ — the connection already scopes the run and gives tab-close cancellation for free; a registry would add state to manage with no current consumer.

3. **Read-only concurrent workers.** Each worker is a sub-agent spawned through the harness's sub-agent API and restricted by the tool filter to `read`, `read_image`, `glob`, and `grep`. Workers never write and return free-form streamed text, so two lanes that share one workspace can run concurrently without ever conflicting over edits.
   - _Rejected: workers with full tool access_ — concurrent lanes editing the same workspace could trample each other's changes.

4. **Single run-factory seam.** The server depends on one injected function — `startRun({ task, primaryModel, laneModels }, onEvent) -> { id, cancel() }`. Production wires it to the harness-backed orchestration (boot the harness, create the orchestrator on the primary model, spawn the two workers, wait for both, emit a comparison summary). Tests inject a fake factory that emits scripted events. This one seam is the only place run behavior is tested.
   - _Rejected: mocking the harness or adding a second seam for the WebSocket protocol_ — a single narrow seam keeps the tested surface small and the tests specification-shaped (submit -> events go to the right lane, cancel stops the run, disconnect cancels the run).

## Considered Options

Beyond the three rejected alternatives above, we considered not capturing these decisions at all; they are recorded because each is a choice a future reader would otherwise re-question: WebSocket versus SSE/polling, per-connection versus registry-backed runs, read-only versus fully-permissive workers, and one seam versus several test points.

## Consequences

- Live streaming and per-tab isolation follow directly from the per-tab WebSocket transport.
- Workers being read-only is the enabling constraint for safe concurrency; a future worker that must write would require reopening ADR-0001.
- Behavior is tested only through the run-factory seam, which keeps tests specification-shaped but leaves the real orchestration verified by manual smoke testing.
