# ADR-0004: codebase simplification — archive the demos, extract the UI, name the product

## Status

Accepted

## Context

The repository had become two projects in one: the active `harness-workflow` web app (an HTTP + WebSocket server serving a static comparison UI, backed by the shared DSH harness) was tangled with two earlier DSH-harness demonstration scripts. The product server embedded its entire UI as one inline template — the largest and least navigable file in the tree, with the browser script effectively unmaintainable markup — and the demos, their demo-only config, and long README walkthroughs occupied product surface without being part of the product. The product also had no name of its own in its own repository.

## Decisions

1. **Archive the demos under `examples/` with a self-contained boot copy.** The two scripts live under `examples/` with their own frozen copy of a generic DSH-harness boot, sharing **no code** with the product. This is deliberate, visible duplication: isolation is worth more than the shared boot it replaces. They remain on disk and greppable as the in-repo reference for the harness agent/streaming API, and they are still type-checked so they do not silently rot against the published harness packages.
2. **Extract the product UI to static assets served per request.** The inline server template became a document plus a stylesheet plus a browser script under `public/`, which the server reads from disk per request — editing the UI needs no server restart, and the server file roughly halves. The browser script was moved verbatim (a mechanical relocation with no behavioral modernization), proved behavior-preserving by the existing HTTP-boundary tests, which now fetch the extracted assets over HTTP.
3. **Untrack the demo-only configuration.** The demo-only config (`dsh-demo.config.json`, and the local overrides it can point at) is untracked from the repository root and gitignored; it only ever served demo isolation. The archived demos keep resolving it from the root, so they keep working with no boot change. The product reads the shared harness home by design (see ADR-0003).
4. **Name the product `harness-workflow` in the tree while `examples/` stays `dsh-demo`.** The runtime boot identity (the name handed to the harness boot and to overlay loading), the npm package name, and every docs/glossary/ADR product-name reference read `harness-workflow`; the archived demos keep the old `dsh-demo` name so the two are visually distinct in one repository. Renaming the repository and the project folder themselves is the maintainer's own follow-up, out of scope here.

## Considered Options

- **Sharing one boot module between the product and the demos.** Rejected: the demos must be isolated from the product so maintaining one never breaks the other; the deliberate duplication under `examples/` is the point.
- **Leaving the UI in the inline server template.** Rejected: it made the server the largest, least navigable file in the tree and left the browser script unmaintainable markup.
- **Keeping the demo config tracked at the root.** Rejected: it is demo-only and never product; the product reads the shared harness home by design (ADR-0003).

## Consequences

- The product and the archived demos are structurally isolated: editing or deleting product code can never touch the demos, and vice versa.
- The product has one real name (`harness-workflow`) distinct from the archived demos (`dsh-demo`) in the same repository.
- The browser-facing contract is unchanged, verified by the existing server-boundary tests exercising the extracted assets over HTTP.
- The demos keep working via the re-pointed `pnpm demo` / `pnpm enhanced` scripts and remain a greppable harness-API reference.
