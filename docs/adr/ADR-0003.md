# ADR-0003: read the shared DSH workspace catalog from the web-app storage stack

## Status

Accepted

## Context

A run's workspace is a folder selected from the shared DSH workspace catalog (owned by DSH web), not a typed path: harness-workflow reads the catalog read-only and never creates or deletes workspaces. The catalog is the `workspace` domain table that DSH web already populates, persisted by a JSON storage backend under the harness home at `$DSH_HOME/storages/workspace.json` (default `~/.dsh/storages/workspace.json`). harness-workflow must read the same table the web UI shows so the picker offers exactly the folders the user manages there.

The web-app bundle composes this storage stack — `storage`, `storage-json` (rooted at the storages directory under the harness home), `storage-domain`, and `workspace` — so `ctx.workspaceRegistry` reads the same table the web UI populates. The base bundle does not ship storage or workspace; they are web-app additions, which makes this composition easy to miss.

## Decision

Compose the web-app storage stack into harness-workflow and read the shared workspace table under the harness home:

- `storage` — the storage hub.
- `storage-json` — the JSON backend, rooted at `$DSH_HOME/storages` (default `~/.dsh/storages`).
- `storage-domain` — the domain layer over the storage hub (`backend: json`).
- `workspace` — the workspace registry over the domain layer, exposing `ctx.workspaceRegistry`.

This only works when harness-workflow and DSH web run under the same harness home (`$DSH_HOME`), because the shared table lives at `$DSH_HOME/storages/workspace.json`. A wrong root — a different harness home, or a storage-json mis-rooted elsewhere — silently boots an empty registry rather than failing loudly: the storage-json root has no default on purpose, and an absent or empty table simply yields no workspaces, which reads as "the catalog is empty".

harness-workflow reads the registry read-only: it never calls a registry mutation (create, delete, insertBefore, archiveSession) nor a workspace-entity mutation (attachSession, detachSession, setTitle, insertSessionBefore).

## Considered Options

- **An isolated workspace table owned by harness-workflow.** Rejected: it would diverge from the catalog the user manages in DSH web, recreating the duplication the shared catalog exists to avoid.
- **Reading the registry file directly, without composing the storage stack.** Rejected: composing the same storage stack as the web-app bundle keeps one shared composition of the same table and mirrors the pattern the web app already follows; a bespoke file read would duplicate the domain schema and validation.

## Consequences

- The workspace dropdown is seeded from `ctx.workspaceRegistry`, so harness-workflow offers exactly the folders DSH web manages, and nothing else.
- Couples harness-workflow to the shared storage layout and to running under the same `$DSH_HOME` as DSH web; a wrong root silently boots an empty registry.
- The session-cwd mechanism of ADR-0002 is unchanged: the registry only seeds the picker; the run still carries the canonical workspace path, which becomes the orchestrator's session cwd.
