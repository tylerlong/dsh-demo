# ADR-0005: rebuild the frontend as a TypeScript + Vite + React single-page application

## Status

Accepted

## Context

The product frontend was a hand-written vanilla document plus stylesheet plus browser script served from disk, with the run lifecycle and DOM wiring in one imperative browser script. It was untyped, unstructured, and hard to maintain: there was no component structure, no state machine, no type safety, no frontend tooling (no hot reload, no component tests, no build step), and the WebSocket contract existed only on the server side while the client re-derived it by hand. The server also carried a fixed per-asset map for exactly the three static files, which had to be hand-edited whenever the frontend changed shape.

## Decisions

1. **Rebuild the product UI as a TypeScript + Vite + React single-page application styled with Tailwind (latest major), and delete the old vanilla assets.** The frontend source lives in its own top-level `web/` directory, distinct from the server source; Vite's root index document (`web/index.html`) is the app's entry. The old `public/` document, stylesheet, and browser script are deleted — nothing is kept for sunk-cost reasons. This supersedes in effect ADR-0004's statement that the browser script was moved verbatim: the browser script is now rewritten, not moved.
2. **One shared protocol module holds the WebSocket contract.** `shared/protocol.ts` — a top-level module in its own directory, distinct from both the server and the frontend source trees — holds the run request shape, the run event union, the lane identity, and the WS path constant. Both the server and the client import it, so the contract cannot drift.
3. **Componentized React UI with the run lifecycle in a dedicated hook.** The app is an app shell (`App.tsx`) holding a run configuration form (`RunConfigForm.tsx`: task, primary model, workspace, submit/cancel), model and workspace selectors (`ModelSelect.tsx` / `WorkspaceSelect.tsx`), and a lane component (`Lane.tsx`) rendered twice. The `useRun` hook owns the WebSocket connection and the run state machine (idle → running → streaming events → done / error / canceled) plus input locking.
4. **Build-then-serve for production.** `pnpm serve` builds the frontend (`vite build web`, output `web/dist`) and then the existing single HTTP + WebSocket process serves the built output. The server's fixed per-asset map becomes a generic static file server over the built output: the index document at the root, a MIME map by extension, and 404 for missing files — the current 404 behavior for unknown routes is preserved.
5. **One-command development.** `pnpm dev` runs the backend and the Vite dev server together (concurrently). The dev server proxies the API routes (`/api/*`) and the WebSocket endpoint (the shared `WS_PATH`) to the backend, so the browser talks to one origin and gets hot reload. The dev proxy honors the same `HARNESS_WORKFLOW_PORT` override the backend reads.
6. **Tests rewritten to fit the new frontend.** The run-lifecycle hook and the form/lane components are unit-tested with Testing Library in a DOM-like environment (jsdom) with a mocked WebSocket, replacing the deleted server-side browser-script wiring suite. The e2e is rewritten against the React DOM (Playwright, local-only, not in CI). The server-boundary suites keep their injected-fake seams and behavior; the static-page suite now fetches the built frontend output, which the tests build in setup.

## Considered Options

- **Keeping the vanilla assets.** Rejected: they are untyped, unstructured, and have no tooling; the rewrite's whole point is a type-safe, componentized, testable frontend with hot reload.
- **Serving the frontend from a fixed per-asset map.** Rejected: it must be hand-edited whenever the frontend changes shape; a generic static file server over the built output needs no server-map edits.
- **A separate frontend process in production.** Rejected: the product keeps one local HTTP + WebSocket process at runtime; the dev workflow is the only place a second process appears.

## Consequences

- The frontend is type-safe, componentized, and unit-testable without a browser; the run lifecycle is verified through what a user sees (events rendered, inputs locked, submit/cancel states).
- The WebSocket contract lives in one shared module, so the server and client cannot drift.
- Production serving is still one command (`pnpm serve` builds then serves), and development is one command (`pnpm dev`) with hot reload.
- The domain vocabulary (run / lane / workspace / worker / orchestrator) is unchanged; the rewrite changes how the UI is built, not what the product does.
