# ADR-0006: session browser — resume a selected session from the shared store

## Status

Accepted

## Context

Today the product page has a single run form: you pick a task, a primary model, a workspace from a dropdown, and a lane model for each lane, then submit. Every submit creates a brand-new session (a fresh `session-<runId>`) and runs the comparison in it from a blank slate. There is no way to revisit what a previous run produced, and no way to continue a session — each run is throwaway, even though the shared DSH session store persists every session's full transcript to disk.

The maintainer wants to copy DSH web's workspace browser shape: a **left panel** listing workspaces, each expandable to its sessions, **read-only** (display only — no creating, deleting, modifying, or reordering workspaces or sessions), loaded once on page load with no auto-refresh. Clicking a session **opens it in the right panel**, which then lets you **continue that session's work**: submitting sends the primary agent to resume that saved session, inheriting its context (not starting from a blank slate), and the run's new turns append to that same session. The right panel keeps its current two-model comparison behavior — the workspace dropdown is removed (the workspace now comes from the selected session), the same two lane workers still do the task after submit, and cancel aborts only the viewed session's run.

The maintainer explicitly does not want the frontend to rebuild agent output from streamed delta events; instead it should **read output from the store** (the shared session store, the same source DSH web uses), showing a recent window of lines rather than the full history, so the frontend reuses DSH web's display approach and loses nothing when switching away and back.

## Decisions

1. **Read-only workspace→session tree from the shared store.** The left panel is a two-level tree — workspace → its sessions — sourced read-only from the shared DSH store: the workspace registry for the workspace list and the session store for each workspace's sessions. Sessions are labeled by their **session id** — the only stable label the read-only listing provides; there is no title field and no title is invented. There is no "Ungrouped" group: sessions appear only under their listed workspace. Nothing creates, deletes, edits, reorders, attaches, or renames on either level. The tree is loaded once on page load and never auto-reloaded. The latest session is preselected and the selected row is highlighted so the user always knows which session and workspace will be used.

2. **Resume, not create, when continuing a session.** Submitting a run resumes the selected session instead of creating a fresh one. The run request carries the selected **session id** — in the shared protocol, `RunRequest.workspace` is replaced by `RunRequest.sessionId` — and the production run factory resumes that session via the harness (`ctx.agents.resume`), so the primary agent inherits the session's saved context and the run's new turns append to that same session. The run's workspace is the resumed session's cwd from its header — it is not taken from the request and not shown in the form.

3. **The workspace dropdown is removed.** The run form keeps the task, the primary model, and the two lane models; the workspace now comes from the selected session instead of a form selection. Submit is disabled until a session is selected, and the task field starts empty. This supersedes in effect ADR-0003's decision that the workspace dropdown is seeded from `ctx.workspaceRegistry` and ADR-0002's submit-time workspace resolution: the workspace now derives from the resumed session's cwd, not a form selection.

4. **Per-run cancel with concurrent runs.** The run handle keeps its `id` and `cancel()`; cancel aborts only the current run — the viewed session's run — while other running sessions continue server-side. Multiple runs may run concurrently across sessions. Sub-agent mechanics are unchanged: the same two read-only lane workers are spawned under the resumed primary agent and do the task after submit.

5. **Output comes from the store, not from streamed deltas.** The right panel renders each agent's output — the primary agent and its two lane-worker children, identified via the `parentSession` header — by reading the store and showing a recent window (~100 lines) rather than the full history, reusing DSH web's display approach. Live progress for the viewed running session is pushed from the server over the WebSocket as session events (mirroring DSH web's event push); history and switch-away/back are a fresh store read. Background runs keep writing to the store server-side regardless of what the frontend shows, so nothing is lost. The streamed text-delta events the old render path consumed are no longer the source of rendered output; the run-lifecycle events (run/started, run/done, run/canceled, lane start/done/error) remain for run state and input locking.

## Considered Options

- **A workspace dropdown that keeps creating a fresh session per run.** Rejected: every run stays throwaway with no way to continue; the whole point is continuing a saved session with its context.
- **A mutable session browser (create/delete/rename sessions or workspaces).** Rejected: the shared DSH store is owned by DSH web; harness-workflow reads it read-only and must never mutate the catalog.
- **Rebuilding the output transcript in the frontend from streamed delta events.** Rejected: the frontend would own transcript assembly, lose everything on switch-away/back, and diverge from DSH web's display approach; reading from the store keeps the frontend thin and nothing is lost when switching sessions.

## Consequences

- Continuing a session inherits its saved context; new turns append to the same session, so no run is throwaway.
- The workspace derives from the resumed session's cwd; the run form no longer selects a workspace.
- Cancel is per-run: the viewed session's run is aborted while other running sessions continue server-side in the store.
- Output rendering is a thin store read (recent ~100-line window) with live pushes; the frontend does not assemble transcripts from streamed deltas.
- The run request contract changes (`sessionId` replaces `workspace`); the shared protocol remains the single contract the server and client share.

## Refinement: readable labels, ordering, and a styled primary-only transcript

The initial design above labeled sessions by their session id and rendered each agent's output — the primary plus its lane-worker children, resolved via `parentSession`. The shipped session browser refines this (tickets #45–#47) while keeping the read-only, store-backed, resume-not-create design intact.

- **Session facts come from the store only.** Each session row's `label` is its stored title read through the store's title projection read face (the base-bundle `session-query` / `session-projection` rows), else a minimal "Untitled session" placeholder. Ordering uses the store's `createdAt` directly. No event-log scanning and no polling — supersedes in effect decision 1's "labeled by their session id".
- **Ordered and focused list.** Sessions within a workspace are ordered by `createdAt` descending (newest first) and capped at the top 3 per workspace; workspaces are ordered by their newest session's `createdAt` descending. Subagent sessions (`origin: 'subagent'`) are filtered out, so the lane-worker children every run spawns never clutter the panel.
- **Primary-only transcript with input/output styling.** The right panel reads only the selected session's own transcript from the store; stored subagent children's histories are never read, so old subagents never render. Each line carries a role: `user/message` → input and `assistant/message` → output each get a distinct background; every other line (tool/step/system) keeps the default panel style — there is no third background. This supersedes in effect the `parentSession`-resolved children in decision 5.
- **Live lanes only while our own run is live.** The two lane-worker children of the in-progress run are supplied in-memory and rendered alongside the primary only while that run is live; once the run settles and they are stored, they are not loaded.
